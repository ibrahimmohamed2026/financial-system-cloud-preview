# Financial System — Backend (FastAPI)

## التشغيل وإعداد PostgreSQL المركزي

**النشر المقترح للشركة:** ثبّت PostgreSQL والتطبيق على سيرفر مركزي، واجعل أجهزة الموظفين تفتح النظام من المتصفح عبر `http://IP-السيرفر:8000`. لا يحتاج كل جهاز موظف إلى تثبيت PostgreSQL.

1. راجع `CENTRAL_POSTGRESQL_SETUP_AR.md` ونفّذ إعداد PostgreSQL على السيرفر.
2. شغّل `setup_and_run.bat`؛ في أول تشغيل سيطلب بيانات اتصال PostgreSQL ويحفظها في `.env`.
3. يتم اختبار الاتصال تلقائيًا قبل تشغيل التطبيق. يمكنك اختباره يدويًا عبر `python check_postgres_connection.py` داخل البيئة الافتراضية.
4. من أجهزة الموظفين افتح `http://IP-السيرفر:8000`، مع السماح بمنفذ TCP 8000 في Windows Firewall من شبكة الشركة فقط.

`DATABASE_URL` أو متغيرات `POSTGRES_*` في `.env` تحدد قاعدة البيانات التي يستخدمها التطبيق. لا تضع ملفات البيانات الفعلية يدويًا داخل مجلد المشروع. الملف `database/postgresql_schema.sql` مخطط للجداول فقط ولا يحتوي على بيانات الشركة.

**حماية البيانات:** لا يحذف إعداد التشغيل قاعدة البيانات أو جداولها. التطبيق قد ينشئ الجداول الناقصة ويحدّث عناصر مخطط إضافية عند بدء التشغيل. لا تنفذ ملف المخطط على قاعدة قائمة تحتوي بيانات قبل أخذ نسخة احتياطية ومراجعة الوضع. لم يتم نقل بيانات SQL Server تلقائيًا؛ راجع `SQLSERVER_TO_POSTGRES_MIGRATION_AR.md`، وابدأ دائمًا بـ `--dry-run` على قاعدة هدف مخصصة وفارغة.

لإنشاء مستخدم أو إعادة ضبط كلمة المرور، استخدم أدوات المشروع بعد التأكد من أن `.env` يشير إلى قاعدة PostgreSQL الصحيحة. لا تشغّل أدوات تهيئة SQLite القديمة على قاعدة الشركة.

## استيراد Excel
1. نزّل القالب من `/accounts/import/template` (فيه قايمة التصنيفات والتعليمات).
2. ارفع الملف بـ `dry_run=true` الأول: بيرجّع عدد الصفوف السليمة وقايمة الأخطاء برقم الصف في الإكسيل.
3. صحّح الأخطاء وارفعه بـ `dry_run=false` للحفظ. الحفظ **كله أو لا شيء**: أي خطأ = مفيش حاجة بتتحفظ (422).
- بيدعم العناوين بالعربي أو الإنجليزي، ويلاقي صف العناوين حتى لو فوقه صفوف عنوان (أول 15 صف).
- الأب ممكن يكون في الملف (حتى لو بعد الابن) أو موجود في النظام. أقصى حجم 5MB و5000 صف.
- الأكواد اللي بتبدأ بأصفار: خلّي عمود الكود نص (القالب جاهز كده) وإلا Excel بيشيل الأصفار.
- التصنيفات لازم تكون موجودة في النظام بنفس الاسم (مش بتتعمل تلقائيًا).
- التصميم الحالي على قالب بسيط؛ لو عايز تستورد من ملف "ميزانيه فارغه.xlsx" مباشرة محتاج mapper مخصوص على شكل شيت Trial balance.

## وحدة العقود والمكتب الفني والمستخلصات (إضافة ERP)

تمت إضافة طبقة جديدة فوق الجداول الحالية، دون حذف أو إعادة تسمية أي جدول قديم:

- `ContractItems`: بنود العقد/جدول الكميات والوحدات والكميات وأسعار الوحدة.
- `ContractChangeOrders`: أوامر تغييرية تمر بحالة `Pending` ثم `Approved`؛ لا تدخل قيمتها ضمن سقف العقد إلا بعد الاعتماد.
- `ContractDeductionRules`: قواعد خصم منفصلة لكل عقد ولكل نوع مستخلص (عميل/مقاول باطن)، مع نسبة أو مبلغ ثابت، أساس الحساب، حد أقصى، حساب الأستاذ العام، وجهة القيد.
- `ContractAccountingConfig`: إعدادات الشركة والسنة المالية وحسابات الرقابة والأعمال والاحتجاز والدفعات المقدمة والضرائب وضريبة القيمة المضافة لكل نوع مستخلص.
- `ContractSettlements`: تسلسل مستقل للمستخلصات لكل عقد ونوع، قيمة الفترة والتراكمي والخصومات الفعلية والضريبة والصافي وحالة الترحيل ورقم القيد.

### تشغيل الترحيل

1. خذ نسخة احتياطية من PostgreSQL قبل أي ترحيل.
2. تأكد من ضبط `.env` و`DATABASE_URL`/إعدادات PostgreSQL كما في بقية النظام.
3. من مجلد المشروع نفّذ `python run_sql.py`؛ سيطبق `sql/007_contract_technical_settlements.sql` بشكل إضافي وقابل لإعادة التشغيل.
4. أعد تشغيل التطبيق ثم افتح `/contracts`، واختر عقدًا. تظهر أدوات المكتب الفني والمستخلصات الجديدة داخل تفاصيل العقد.
5. أضف إعدادات المحاسبة لكل من مستخلص العميل ومقاول الباطن، ثم عرّف قواعد الخصم وحساباتها قبل إنشاء مستخلص يحتاجها.
6. المستخلص يبدأ `Draft`؛ بعد المراجعة اعتمده، ثم رحّله. يمنع النظام تكرار الترحيل ويرفض القيد غير المتوازن أو السنة المالية المغلقة.

### واجهات API الجديدة

- `GET/POST /api/contracts-erp/{contract_id}/technical-items`
- `GET/POST /api/contracts-erp/{contract_id}/change-orders` و`POST /api/contracts-erp/change-orders/{id}/approve`

**ملاحظات محاسبية:** قواعد الخصم ليست نسبًا ثابتة في الكود؛ الحسابات والنسب والأساس والحدود قابلة للضبط لكل عقد. يتطلب الترحيل حسابًا فعالًا وسنة مالية مفتوحة. بالنسبة لمستخلص العميل، قواعد الخصم التي تظهر في القيد يجب أن يكون اتجاهها `Debit` (مثل المحتجز/الضريبة المخصومة/استرداد السلفة وفق المعالجة المعتمدة)، أما مستخلص مقاول الباطن فيجب أن تكون `Credit` (مثل المحتجز والضرائب والدفعات المستردة). أي معالجة مختلفة تحتاج مراجعة إعدادات القيد وسياسة الشركة قبل استخدامها.

**حدود التحقق:** تم إجراء فحص ترجمة Python وJavaScript وفحص إنشاء المخطط باستخدام SQLite مؤقتة. لم يتم الاتصال بقاعدة PostgreSQL الخاصة بالشركة أو ترحيل بيانات فعلية في بيئة البناء؛ اختبر على نسخة احتياطية/بيئة تجريبية أولًا.

## استكمال الشاشات التي كانت تعرض «قيد التنفيذ»

تم ربط شاشات منفصلة جديدة في الواجهة:
- `/settlements`: مستخلصات العملاء ومقاولي الباطن، مع عرض المستخلصات واعتمادها وترحيلها محاسبيًا بعد ضبط حسابات العقد.
- `/inventory`: تعريف الأصناف والمخازن، عرض الأرصدة، وتسجيل حركات الوارد والمنصرف مع منع الصرف الذي يتجاوز الرصيد.
- `/purchases`: إنشاء أوامر الشراء، اعتمادها، واستلامها إلى المخزن مع توليد حركة وارد تلقائية وتحديث الرصيد.

الجداول الإضافية هي `InventoryItems`, `InventoryWarehouses`, `InventoryMovements`, `PurchaseOrders`, و`PurchaseOrderLines`. تُنشأ بطريقة إضافية بواسطة `Base.metadata.create_all` عند تشغيل التطبيق؛ لا تحذف أو تعيد إنشاء الجداول المالية القديمة. عند استخدام حسابات مستخدمين غير Admin، امنح صلاحيات `Contracts`, `ContractSettlements`, `InventoryManagement`, و`PurchaseCycle` من شاشة إدارة الصلاحيات.

حدود النسخة الحالية: نموذج أمر الشراء في الواجهة ينشئ بندًا واحدًا لكل أمر في هذه المرحلة، بينما يدعم مخطط قاعدة البيانات وواجهة API أكثر من بند؛ كما أن استلام أمر الشراء ينفذ استلامًا كاملًا للكميات المتبقية، وليس استلامًا جزئيًا. لم يتم اختبار الاتصال على قاعدة PostgreSQL الفعلية الخاصة بالمستخدم.

## تحديث المستخلصات وربطها بكميات العقد
- أضيف جدول `ContractSettlementItems` لتسجيل كمية كل بند وسعر الوحدة وقيمة البند داخل المستخلص، مع الاحتفاظ بجدول المستخلصات الحالي دون حذف بيانات.
- عند وجود بنود فنية للعقد، يجب إنشاء المستخلص من شاشة «المكتب الفني» وتحديد كميات البنود؛ يحسب النظام قيمة الأعمال تلقائيًا ويرفض القيمة اليدوية غير المطابقة.
- شاشة العقد تعرض إجمالي المستخلصات السابقة المعتمدة/المرحّلة، والأعمال التراكمية، والمتبقي من قيمة العقد، لكل من مستخلصات العميل ومقاول الباطن.
- المسودات لا تدخل في الإجمالي السابق. عند الاعتماد يعيد النظام فحص الكميات تحت قفل العقد لمنع اعتماد مسودتين متعارضتين تتجاوزان الكمية التعاقدية.
- إضافة `sql/008_contract_settlement_item_details.sql`، وتنفذ تلقائيًا من `run_sql.py` على PostgreSQL. لا تحذف الترحيلة أي جدول أو بيانات قائمة.
- العقود التي لا تحتوي على بنود فنية تظل تدعم إدخال قيمة أعمال إجمالية كمسار قديم. بمجرد إضافة بنود فنية، تُمنع شاشة المستخلصات القديمة من تجاوز مسار الكميات.

## مرفقات العقود والمستخلصات
- من تفاصيل العقد افتح قسم «المرفقات والمستندات» لرفع العقد الموقع، السجل التجاري، البطاقة الضريبية، بيانات الشركة/المقاول، بيانات الحساب البنكي، عروض الأسعار، وخطابات الإسناد.

- الصيغ المسموحة: PDF، PNG/JPG/WEBP، DOC/DOCX، XLS/XLSX، CSV، TXT، ZIP وRAR. الحد الأقصى 20 ميجابايت لكل ملف.
- تحفظ بايتات الملف في جدول `ContractAttachments` داخل قاعدة البيانات، وليس في مجلد عام؛ لذلك تدخل في نسخ قاعدة البيانات الاحتياطية. تنزيل الملف محمي بتسجيل الدخول وصلاحية العرض المناسبة، والرفع محمي بصلاحية الإضافة.
- عند بدء التشغيل ينشئ `ensure_schema` الجدول تلقائيًا. يوجد أيضًا ملف SQL مرجعي باسم `sql/012_contract_attachments.sql` لبيئات PostgreSQL.

## ملف قاعدة بيانات PostgreSQL داخل المشروع

ملف إنشاء المخطط موجود في `database/postgresql_schema.sql`، وتعليمات إنشائه عبر pgAdmin في `DATABASE_POSTGRESQL_AR.md`. الملف ينشئ هيكل الجداول الحالي ولا يحتوي على بيانات الشركة. PostgreSQL قاعدة بيانات خادمية، لذلك لا تكون قاعدة البيانات الفعلية ملفًا واحدًا داخل مجلد المشروع.

## ربط بنود العقود والمستخلصات والمخازن بشجرة الحسابات

- من شاشة **إدارة المخزون** استخدم «بند مركزي وربطه بحساب» لتعريف البند (مثل توريد بازلت 50/100)، واختيار حساب تفصيلي نشط من شجرة الحسابات. عند الحاجة اربطه بصنف مخزني.
- عند إضافة بند فني للعقد يظهر فلتر حساب، ثم قائمة البنود المركزية التابعة للحساب المختار. الكمية وسعر الوحدة والإجمالي تحفظ كسطر عقد، ويستفيد المستخلص من أسطر العقد نفسها مع فلتر الحساب وكميات الإنجاز.
- عند ترحيل المستخلص، يرحّل النظام قيمة كل بند إلى حسابه المرتبط، مع إبقاء حسابات الرقابة والضريبة والخصومات من إعدادات العقد. البنود القديمة غير المربوطة تظل تستخدم حساب الأعمال القديم.
- زر «مستند متعدد البنود» في المخزن يقبل عدة أسطر، مع فلترة البنود بالحساب المرتبط، ويعالج المستند كوحدة واحدة لمنع حفظ جزء منه عند نقص الرصيد. حركات المخزون تظل حركة كمية/تكلفة كما في النظام الحالي؛ لا تنشئ قيود أستاذ تلقائيًا لأنها تحتاج إعداد حساب المقابل/التقييم المخزني.
- ترحيل قاعدة البيانات إضافي عند بدء التطبيق: ينشئ جدول `ItemCatalog` ويضيف أعمدة اختيارية إلى جداول بنود العقد والمستخلص دون تعديل أو حذف السجلات القديمة. أعد تشغيل التطبيق لتطبيقه.
